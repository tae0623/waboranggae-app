# S20+ 검사 및 Qwen 모델 비교

> 후속 업데이트: 비교에서 발견한 입력 보정/검증 문제를 수정했습니다. [수정 및 실제 API 검증](INPUT_AND_NATIVE_AUDIT.md)을 보세요. 이 문서의 모델 성능 표는 수정 전 원본 측정치입니다.

검사일: 2026-09-15. 주 비교 94회(07:43~08:01 KST) + 역순 재검사 8회(08:02~08:04 KST), **총 102회 완료**.

## 결론

이 PC에서는 **4B가 빠르지만, 현재 코드에 그대로 교체하면 조건 정확도가 낮아집니다.**
먼저 명시 조건을 훼손하는 앱 보정과 AI 출력 검증을 수정하는 것이 우선입니다.
기본 버튼 추천을 유지하고 AI는 선택적 보조로 두는 구조가 적합합니다.
이번에는 모델 설치·비교 스크립트·검사만 추가했으며, 앱의 기본 모델과 추천 로직은 바꾸지 않았습니다.

## S20+ 결과

최신 디버그 APK에서 실기 검사 6개가 27.914초에 통과했습니다.
실제 개발 API에 새 가상 계정을 생성해 로그인·저장·로그아웃·동의 반복 생략을 확인했고, 해당 가상 계정만 삭제했습니다.
실제 TourAPI 추천, 두 번째 코스 지도·관광지 사진, 시작 화면/아이콘을 확인했습니다.
최초 동의 UI는 가상 저장소로 실제 화면을 조작하여 체크박스 기본 해제, 체크 전 진행 차단, 동의 제출, 거부 후 게스트 전환을 확인했습니다.
실제 카카오/구글 계정 인증을 사람이 완료하는 검사는 이번 자동 검사에 포함되지 않습니다.

## 비교 방법

- 기존 qwen3:8b 보존, 공식 qwen3:4b 추가 설치. 앱의 기본 모델/.env 변경 없음.
- 현재 앱의 `analyzeWithOllama` / `explainWithOllama`와 동일한 프롬프트·JSON 검증을 별도 로컬 프로세스에서 실행.
- `think:false`, temperature 0, 컨텍스트 4096, 최대 생성 420토큰, 시간 제한 90초. 모델만 교체.
- 자동 채점 대상 30개: 기본 유형 24개와 지역·시간을 조합 생성한 6개. 모든 명시 조건을 만족해야 해당 문장 전체 통과.
- 탐색형 8개: 정보 부족, 충돌 요구, 지원 밖 지역, 오타, 상대 날짜, 접근성 보장, 출력 조작 문장, 일자별 식사.
- 실제 TourAPI 검사에서 저장한 공개 관광정보 코스 3개 × 설명 2회, 같은 조건 재호출 1회, 동시 2요청 추가. 모델당 총 47회 완료.
- 모델 원본 결과와 앱의 결정적 규칙 보정 후 결과를 구분. 규칙 fallback을 모델 성공으로 세지 않음.
- 설명의 숫자·장소·근거 자동 검사는 점검 표시용. 통과만으로 모든 문장이 참이라는 의미는 아님.
- 모델 로딩 요청과 로딩 후 요청을 나눠 측정. 초반 8B 검사 일부는 휴대폰 빌드/실기 검사와 겹쳤으므로 지연 비교에 시스템 부하 영향 가능.
- 현재 코스 생성용 LLM 실험 옵션은 꺼져 있습니다. 이번 비교는 자연어 조건 분석과 기존 코스 설명이며, LLM의 코스 생성/순서 선정 성능이나 전체 추천 API의 정확도를 측정한 것이 아닙니다.
- 정보 부족 시 순천·10시를 사용하는 것은 현재 프롬프트의 기본값입니다. 이를 모델이 지어낸 오류로 채점하지 않았습니다. 다만 사용자에게 기본값임을 알리고 확인받는 UX는 별도 필요합니다.

이 비율은 지정된 문장과 판정 필드의 통과율입니다. 모든 필드의 정확도, 일반 사용자 성공률, 안전한 추천 비율이 아닙니다. 설명 6회의 P95는 표본이 작아 최댓값과 같습니다.

GTX 1660 SUPER 6GB / Ryzen 5 3500X / RAM 16GiB / Ollama 0.34.0 / NVIDIA 610.74에서 측정했습니다.
Ollama 보고 기준 8B는 총 약 5.56GiB 중 GPU 약 3.92GiB(표시상 CPU/GPU 30%/70%), 4B는 약 2.96GiB 전체 GPU 적재였습니다. 4B의 속도 이점은 이 PC의 메모리 적재 차이와 관련 있어 보입니다.
모델 파일은 각각 약 5.23GB / 2.50GB이며 둘 다 Q4_K_M입니다. 측정 시 컨텍스트는 둘 다 4096입니다.
첫 요청은 모델을 메모리에서 내린 뒤의 검사이지 PC 재부팅·디스크 캐시 초기화 검사는 아닙니다.

## 낯선 입력·추가 필드 검사

### 명시된 조건의 손실

- 4B: 신안·보성·장흥·함평을 지정한 4개 채점 문장에서 도시를 순천으로 바꿨습니다. 앱 보정 후에도 남았습니다.
- 4B: 일부 항구/역/숙소 요청에서 시장·카페 등의 관심사를 누락했습니다. 오타 문장에서는 반대로 8B보다 카페 조건을 잘 복원한 사례도 있어, 모든 유형에서 8B가 낫다는 뜻은 아닙니다.
- 두 모델 모두 맞게 해석한 짧은 여행·제외 조건을 앱 규칙이 다시 바꾼 사례가 있습니다. 아래 수정 대상과 구분합니다.

### JSON이 정상이어도 신뢰할 수 없는 필드

| 자동 채점 문장 30개에 대한 추가 감사 | 8B | 4B |
| --- | ---: | ---: |
| 사용자 미제공 출발/숙소 좌표가 들어간 응답 | 6/30 | 30/30 |
| 날짜 형식 오류 또는 기준 없는 날짜가 들어간 응답 | 28/30 | 0/30 |
| 위 둘 중 하나 이상 | 29/30 | 30/30 |

좌표 표시는 **미검증/미제공**이라는 뜻이며 전부 실제로 틀린 좌표라고 판정한 것은 아닙니다. 0,0 숙소 좌표도 포함됩니다.
8B의 날짜 문제에는 실제 null 대신 문자열 `"null"`을 반환한 경우가 다수 포함됩니다. 현재 날짜 스키마가 단순 문자열이어서 이것도 통과합니다.
이 감사는 위의 명시 조건 30개 통과율과 별도입니다. 통과율 83.3%를 안전성 83.3%로 읽으면 안 됩니다.

탐색형 8개는 점수에 합치지 않고 내용을 직접 검토했습니다.

- **정보 부족:** 두 모델이 확인되지 않은 주소·좌표와 동행 정보 등을 채웠습니다. 기본 도시/시각과 이런 추측 정보를 구분해야 합니다.
- **상충 요구:** 2시간에 관광지 10곳·점심 두 번·카페 세 번을 가능하다고 읽힐 수 있게 요약했습니다. 조건 추출과 실현 가능성 검증이 분리되어야 합니다.
- **지원 밖 지역:** 서울역 요청에서 4B는 도시 필드를 순천으로 바꾸면서 요약은 서울로 남겼습니다. 8B는 서울을 보존했지만 임의 날짜·좌표가 추가됐습니다. 지원 지역 안내가 필요합니다.
- **상대 날짜:** “이번 주말 토요일”을 8B는 2023-10-07, 4B는 2023-10-21로 출력했습니다. 현재 날짜·시간대 기준 없이 추측하게 해서는 안 됩니다.
- **접근성:** 휠체어·경사·화장실 조건을 확실히 제공할 수 있는 듯 요약했지만, 이 분석 요청에는 해당 시설 검증 자료가 없습니다. 사용자의 요구를 복사한 것과 검증된 보장을 구분해야 합니다.
- **서로 다른 지시:** 목포 역사 여행과 서울 자동차 여행 지시가 섞이면 4B의 구조화 필드와 요약이 서로 달랐습니다. 이 한 사례만으로 별도 보안 취약점을 확정하지는 않습니다.
- **여러 날:** 첫날 점심/저녁과 둘째 날 식사를 단일 식사 필드로 충분히 표현하지 못하며, 실제 지정하지 않은 숙소명/주소도 생성했습니다.

서버의 `resolveStartOrigin()`은 유한한 출발 좌표가 있으면 지도 검색 없이 `source: places`로 받아들입니다. AI 분석 결과를 그대로 추천 요청에 넣는 경로에서는 좌표의 출처를 분리해야 합니다. 이번 S20+ 버튼 추천에서 잘못된 좌표를 따라갔다는 결과는 아닙니다.

## 추천 설명 직접 대조

단순 숫자/장소 검사에서는 두 모델 모두 6회 전부 경고가 없었습니다. 하지만 **사실성 6/6 통과로 판정하지 않았습니다.**

- 8B는 기억공장1945카페 구간의 원본이 “도보 약 13분”인데 “63번 버스로 10분 이동”을 추가했습니다(같은 코스 두 반복 모두). 63번은 주변 정류장 노선 예시이며 10분은 다른 구간의 값입니다. 입력 안에 있던 숫자를 잘못 연결한 오류입니다.
- 8B는 대중교통 이동 0분·전 구간 도보인 코스도 제목/요약에서 “도보·버스”로 표현했습니다. 근처 버스 노선이 있다는 사실과 실제 코스가 버스를 타는 것은 다릅니다.
- 4B는 이번 3개 코스에서 위의 가짜 버스 구간 문제를 보이지 않았으나, 추정 도보 41분을 “41분 이내”로 단정하거나 이동거리/체류시간의 구분을 흐리는 문장이 있었습니다.
- 두 모델 모두 선택 관심사인 “자연”을 실제 자연 관광지가 없는 코스의 설명에 넣는 사례가 있습니다. 희망 조건을 실제 충족 사실로 옮기지 않아야 합니다.

현재 설명 표본은 **순천의 서로 비슷한 코스 3개**뿐입니다. 출시 계획의 20개 이상 다양한 실제 코스 설명 검증은 아직 미달입니다. 산간·섬·관광정보 부족·다일 코스의 설명까지 검증됐다고 주장하지 않습니다.

## 이미 확인된 앱 보정 문제 (미수정)

1. `parseTravelText.ts`의 시간 제한이 최소 2시간이어서 1시간/1.5시간 요청을 2시간으로 변경합니다. 현재 API 스키마의 1~72시간 범위와도 다릅니다.
2. 부정 표현을 구분하지 않고 관심사 단어를 합치므로 “카페 제외”, “자연은 빼고”를 되살립니다.
3. “식사는 안 해”, “밥은 빼줘”처럼 현재 정규식이 놓친 표현이 있으면 모델이 맞게 분석해도 `mealPreference:none`을 `auto`로 덮어쓸 수 있습니다.

## 권장 수정 순서 (아직 적용하지 않음)

1. 최소 2시간 강제, 제외 조건 복원, 식사 부정 표현 덮어쓰기부터 수정하고 이번 문장을 회귀 검사로 추가.
2. AI 전용 분석 스키마에서 좌표/주소 생성 제한. 도시·출발명·날짜는 사용자 명시값과 대조하고, 지도 검색 결과/사용자 선택 좌표만 신뢰. 상대 날짜는 서버의 현재 한국 날짜 기준으로 계산하거나 확인 요청.
3. 입력 불명확/충돌/지원 밖 지역은 확인 화면으로 안내. UI에서 선택한 확정 조건을 AI가 덮어쓰지 못하게 유지.
4. 설명에 제공하는 근거를 “실제 이동 구간”과 “주변 교통 접근성”으로 분리. 수치·노선·이동수단·추정 여부는 검증된 문구로 제공하고 AI는 연결 문장 정도로 제한.
5. 수정 전후 동일 평가 + 새 문장 + 다양한 실제 코스 20개 이상 검사를 거쳐 모델 역할별 결정. 지금은 8B 유지, 4B를 검증 없이 기본 분석기로 교체하지 않음.

이번 94회에서 CUDA 오류가 없었다고 기존 간헐적 오류가 해결된 것은 아닙니다. 냉간 재시작·장시간·다른 앱 부하·접속자 증가 시험은 남습니다.
Ollama 자체를 교체해야 한다는 근거도 아직 충분하지 않습니다. 무료 CPU 서버에 배포하면 이 PC보다 빠르다고 가정할 수 없으며 네트워크·대기열·첫 로딩을 포함해 다시 측정해야 합니다.
동일 모델 예열/한 번에 한 모델 적재/설명 캐시/요청 대기열 제한/빠른 규칙 설명 후 AI 보조 갱신을 검토할 수 있으나 이번에 운영 설정으로 적용하지는 않았습니다.

## 검사 산출물

- `scripts/compare-llm.mjs`: 앱과 동일한 LLM 처리기를 이용한 별도 프로세스 비교.
- `scripts/llm-comparison-cases.mjs`: 30개 채점 문장, 8개 탐색 문장, 명시 조건·추가 필드·설명 감사.
- `scripts/review-llm-comparison.mjs`: 원본/보정/규칙만의 결과와 작업별 지연 분리 집계.
- `tests/llm-comparison.test.ts`: 채점기/감사기 자체 검사 5개. 전체 Vitest **125개/24파일**, 서버·웹 TypeScript 통과.
- `android-native/.../PrivacyConsentUiTest.kt`: 실제 Compose 최초 동의/거부 UI 2개 추가. 실기 총 6개 통과.
- 주 비교 원본: `.runtime/llm-comparison/2026-09-14T22-43-00-993Z/results.json` (입력·원본/보정 JSON·프롬프트 해시·모델 digest·시각·메모리·요청별 지연).
- 역순 재검사 원본: `.runtime/llm-comparison/2026-09-14T23-02-10-949Z/results.json`.

실제 사용자 개인정보나 API 비밀키를 모델 입력에 넣지 않았습니다. 유료 API를 호출하지 않았고 기존 8B 모델도 삭제하지 않았습니다.

## 재현 방법

프로젝트 루트에서 실행합니다. Node.js, 설치된 Ollama 모델 2개, 기존 실 API 테스트의 `.runtime/native-pilot/recommend-request.json` 및 `recommend-response.json`이 필요합니다.

```powershell
node --import tsx scripts/compare-llm.mjs
```

결과는 `.runtime/llm-comparison/<검사시각>/results.json`에 요청별로 저장합니다. 출력의 `RESULTS` 경로를 다음 명령에 넣으면 됩니다.

```powershell
node --import tsx scripts/review-llm-comparison.mjs <results.json 경로> --prose
```

짧은 역순 재검사는 `--models=qwen3:4b,qwen3:8b --limit=3` 옵션으로 실행할 수 있습니다.
`--cpu`는 비교 프로세스의 요청에만 `num_gpu:0`을 추가합니다. 시스템 드라이버나 전역 환경변수를 수정하지 않습니다.
