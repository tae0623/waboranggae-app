# 계정 화면 수정 및 이메일 인증·복구 검토

검토일: 2026-09-18. 현재 자체 회원 인증 API + Supabase PostgreSQL/Edge Functions 구조를 기준으로 검토했습니다. Supabase Auth를 사용하는 구조가 아닙니다.

## 이번 반영

- Android 앱 정보에 `앱 버전 v1.0.0`을 표시합니다. 실제 값은 `BuildConfig.VERSION_NAME`을 읽으므로 빌드 버전이 바뀌면 함께 바뀝니다.
- 웹 앱 정보도 프로젝트 package.json의 버전을 읽어 표시합니다.
- Android 로그인 화면에서 개인정보·데이터 출처 링크를 제거했습니다. 회원가입에는 개인정보 수집·이용 동의와 개인정보 전용 상세 안내를 유지했습니다.
- 신규 소셜 계정 동의 화면도 개인정보 안내만 표시합니다. 데이터·이미지·글꼴 라이선스 안내는 내 여행 → 앱 설정에 그대로 유지됩니다.
- 이메일 인증·복구는 아래와 같이 검토했으며, 이번에는 가입 정책·DB·발송 서비스를 변경하지 않았습니다.

## 현재 구현에서 확인한 점

| 항목 | 현재 상태 | 출시 전 보완 권장 |
| --- | --- | --- |
| 이메일 가입 | 형식 검증 후 계정과 로그인 토큰을 바로 생성 | 이메일 소유 확인 후 계정 활성화 |
| 가입 제한 | 기본 메모리 저장소로 IP 기준 시간당 3회 | 서버 인스턴스 간 공유되는 제한 + 이메일별 재발송 제한 |
| 로그인 제한 | 실패한 요청을 IP 기준 15분당 5회 제한 | 다중 인스턴스에서도 동일하게 적용되는 제한 |
| 이메일 인증 | 인증 상태·일회용 인증 토큰 저장 구조 없음 | 인증 시각, 만료, 1회 사용, 시도 횟수 관리 |
| 비밀번호 | bcrypt 해시만 저장 | 원문 찾기가 아닌 비밀번호 재설정 구현 |
| 계정 복구 | 복구 API·메일 발송 연동 없음 | 검증된 이메일로 재설정 링크 발송 |
| 이메일 중복 | 입력 문자열에 대한 DB 유일성 제약 | 앞뒤 공백·대소문자 처리 정책 통일 및 기존 중복 검토 |

근거 코드: `server/src/auth/routes.ts`, `server/src/middleware/rateLimiter.ts`, `server/src/utils/crypto.ts`, `prisma/schema.prisma`.

가입 제한은 프로세스 메모리에 저장되므로 재시작하면 초기화되고 다른 인스턴스와 공유되지 않습니다. 프록시 뒤의 IP 구분도 실제 배포 환경에서 검증해야 합니다. 이메일 인증만으로 한 사람이 여러 계정을 만드는 것을 완전히 막을 수는 없습니다.

## 권장 흐름 — 아직 미구현

1. 이메일·비밀번호·닉네임과 개인정보 동의를 입력합니다.
2. 임시 가입 상태를 만들고 이메일로 일회용 인증 링크를 보냅니다. 이메일 확인 전 일반 계정 권한을 주지 않습니다.
3. 링크의 만료·1회 사용 여부를 확인한 뒤 가입을 완료합니다. 일반 링크 미리보기가 인증을 소모하지 않도록 확인 동작을 구분합니다.
4. 비밀번호 분실 시 등록 이메일에 일회용 재설정 링크를 보냅니다. 가입 여부와 관계없이 동일한 응답을 보여 이메일 가입 여부가 노출되지 않게 합니다.
5. 확인된 사용자만 새 비밀번호를 설정할 수 있게 하고 기존 세션을 무효화합니다. 비밀번호 원문은 메일·로그·DB에 저장하지 않습니다.
6. 재발송 대기, 이메일별·IP별·전체 발송량 제한, 봇 확인을 적용합니다. 토큰 원문은 DB에 저장하지 않고 해시만 저장하며 사용 시 원자적으로 소모합니다.

인증 유효기간·재발송 간격은 구현 시 정할 정책입니다. 예시: 인증 링크 15분, 재발송 60초 대기. 서버에서 강제하고 UI만으로 제한하지 않아야 합니다.

현재 아이디는 이메일입니다. 이메일 자체를 잊은 사용자를 닉네임만으로 식별하거나 전체 이메일을 공개하면 안 됩니다. 별도 검증된 복구 수단이 없는 현재 구조에서는 안전한 자동 아이디 찾기를 제공하기 어렵습니다. 로그인 중이라면 내 여행에서 이메일을 확인할 수 있고, 소셜 계정은 카카오·구글에서 해당 계정을 복구하도록 안내합니다.

기존 이메일 계정도 현재는 소유 확인되지 않았습니다. 신규 인증 도입 시 기존 계정을 자동으로 인증 완료 처리하거나, 같은 이메일이라는 이유만으로 소셜 계정과 합치면 안 됩니다. 기존 계정 데이터의 소유 확인·전환 절차가 필요합니다.

## 비용 및 외부 설정

- Cloudflare Turnstile에는 무료 플랜이 있습니다. 계정 생성 남용 완화를 위한 후보이며, 네이티브 앱에는 별도 웹 기반 인증 화면 및 서버 토큰 검증 연동이 필요합니다. [공식 플랜](https://developers.cloudflare.com/turnstile/plans/)
- Resend 무료 플랜은 현재 월 3,000통·하루 100통입니다. 가입 인증, 재발송, 비밀번호 복구 발송량을 합쳐 보호 한도를 적용해야 합니다. [공식 가격](https://resend.com/pricing)
- Resend 발신에는 소유한 도메인의 DNS 인증이 필요합니다. 기존 Gmail 주소나 pages.dev 주소만으로 발신 도메인을 인증할 수는 없습니다. 도메인이 없다면 구입 비용이 발생할 수 있으므로 완전 무료라고 확정하지 않습니다. [도메인 조건](https://resend.com/docs/dashboard/domains/introduction)
- Supabase 기본 발송은 Supabase Auth용이며 운영용 발송 수단으로 권장되지 않습니다. 현재 자체 인증 구조에는 대시보드 SMTP 설정만으로 연결되지 않습니다. [공식 SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)
- 외부 메일 발송 사업자에 이메일 주소가 전달되므로 적용 전 처리방침·위탁 및 국외 처리 안내도 실제 서비스 설정에 맞춰 검토해야 합니다. 비용·약관 동의나 외부 서비스 계정 생성은 이번 작업에 포함하지 않았습니다.

비용 없이 당장 공개해야 하는 경우의 대안은 게스트·소셜 로그인 중심으로 운영하고 일반 이메일 신규 가입을 준비 완료 후 여는 것입니다. 기존 이메일 계정의 접근·탈퇴를 막으면 안 됩니다. 이 정책 전환은 사용자 결정 없이 적용하지 않았습니다.

보안 흐름 참고: [OWASP 비밀번호 복구 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
