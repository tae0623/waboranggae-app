# 입력 검증 수정 · 네이티브 API/점수 확인

후속 업데이트: 아래는 1차 감사 당시의 기록입니다. 관광사진/수요 강도 호출 오류는 이후 수정했으며, 실제 세 API와 홈 이미지 7개 검증 결과는 [홈 API 복구 기록](HOME_API_FIX.md)을 참고하세요.

검사일: 2026-09-15. 입력 처리 코드는 수정했고, 홈 데이터/점수는 구현 여부를 검사했습니다. 홈 API 주소나 점수 계산식은 이번에 바꾸지 않았습니다.

## 1. 반영한 입력 수정

- 1시간/1.5시간을 최소 2시간으로 바꾸던 보정 제거. 1~72시간 범위 검증, `1시간 30분` 처리.
- 카페·자연 제외, `식사는 안 해`/`밥은 빼줘`/`식사는 하지 않을래` 처리. 관심사 부정의 범위를 다른 문장/쉼표 뒤로 퍼뜨리지 않음.
- 명시한 도시·역/터미널/선착장·시간·취향을 우선. 거절한 출발지와 여객터미널을 역/버스터미널로 바꾸는 오류 방지.
- 식사 제외 시 모델의 `meals: [dinner]` 등이 남지 않도록 식사 필드 동기화.
- AI 전용 스키마에서 좌표·주소·숙소명·날짜·종료시각 생성 필드를 분리. 이전 형식 결과를 보정해도 생성된 좌표/주소는 삭제. UI에서 검색·선택한 추천 요청의 실제 좌표는 그대로 보존.
- 현재 한국 날짜 기준으로 오늘/내일/모레·이번/다음 주의 명시 요일 해석. 연도가 없는 날짜나 일자별 복잡한 요구는 확인 요청.
- 존재하지 않는 날짜, 범위 밖 시간, 시각·총기간 불일치는 모델 호출 전에 HTTP 400과 안내 반환. 추천 API의 날짜 필드도 실제 달력 날짜로 검증.
- 보정 전 모델 요약이 정정한 조건과 모순되거나 접근성을 보장하지 않도록 최종 분석 요약을 확인된 조건으로 다시 구성.

변경 코드: `src/domain/travelInput.ts`, `src/domain/parseTravelText.ts`, `server/src/shared/schemas.ts`, `server/src/modules/analysis/{ollama,routes}.ts`.
기본 LLM은 **qwen3:8b 그대로**이며 유료 API를 사용하지 않았습니다. 추천 설명의 별도 근거 검증 개선은 이번 입력 수정에 포함하지 않았습니다.
이는 범위가 정해진 한국어 입력 처리 개선이며 모든 자연어·오타·부정·복수 도시 요구의 완벽한 이해를 보장하지 않습니다. UI 조건 선택이 기본입니다.

### 검증 결과

- TypeScript 서버/웹 통과. 전체 Vitest **189개/26파일** 통과.
- 기존 30개 문장: 순수 규칙과 의도적으로 틀린 모델 결과 보정 검사 통과.
- 이전 비교의 8B/4B 원본 30개씩을 새 보정에 재입력: **각 30/30** 명시 조건 일치. 이는 저장 응답 재생이지 새 모델 정확도 100% 측정이 아님.
- 최종 실제 `/api/analyze` 검사 **9/9** 통과: 정상 6개는 실제 Ollama 응답 후 조건 보존, 잘못된 입력 3개는 400 거부. 정상 호출 약 11.1~14.4초, 거부 4~16ms. 소규모 표본이며 성능 보장 아님.
- 실제 추천 API의 기존 UI 요청과 TourAPI 코스 5개 수신 확인. 선택 좌표 유지.
- 팀 API 서버 재시작으로 반영. DB·공유 터널·기존 계정·설치 APK는 변경하지 않음.

원본: `.runtime/input-regression/results.json`. 재현: `node --import tsx scripts/verify-input-regression.mjs`.

## 2. 홈 축제/이미지 연계

네이티브 `TravelRepository.hotPlaces()` → `/api/hot-places` → 웹과 같은 서버 서비스를 사용합니다.
홈 배경은 `/api/login-photo`, 사진은 `/api/media/tour-image` 프록시를 거칩니다.
`WebHome.kt`는 축제 카드, 기간, 상세, 사진 출처를 렌더링합니다. Kotlin 모델에도 수요 지표·축제·사진 관련 응답 필드가 있습니다.

| 데이터 | 코드 연결 | 실제 호출 결과 |
| --- | --- | --- |
| 국문 관광정보 `KorService2` | 축제/장소/상세/대표 사진 | 정상. `searchFestival2` 200, 결과 코드 0000. 홈에 축제 3건 + 관광지 3건 |
| 지역 수요 지표 | `TatsStayngService1` + `TatsCnsmrService1` 조회 후 지역 정렬 | 현재 주소 모두 400, “해당 오픈API 서비스가 없거나 폐기됨” |
| 방문자 수 대체 조회 | `DataLabService/locgoRegnVisitrDDList` | 403, “등록되지 않은 서비스키” |
| 관광사진 전용 | `PhotoGalleryService2/gallerySearchList2` | 현재 주소 400, “해당 오픈API 서비스가 없거나 폐기됨” |
| 화면 이미지 | TourAPI 사진 대체 경로 | 홈 배경/축제 사진 각각 200 `image/jpeg`, 실기 표시 확인 |

따라서 **세 종류 모두 정상 연계 완료는 아닙니다.** 현재 수요 정렬은 여수→순천→목포…의 고정 지역 순서로 대체되고, 각 장소 카드 지표는 `관광정보`, 방문자 수 0으로 내려갑니다. 축제/관광지 자체는 실제 TourAPI 자료입니다. 임의 순위의 내부 100/94점은 실제 수요 점수로 화면에 표시하지 않습니다.
관광사진 전용 API 실패 시 배경은 국문 TourAPI 사진을 사용합니다. 축제 사진은 원래 국문 관광정보의 대표 사진을 우선 쓰고, 없을 때 관광사진 검색을 시도하는 구조입니다.
수요 API는 축제의 개최 일정 출처가 아니라 **지역 정렬용**입니다. 지역 지수를 개별 축제의 방문자 수로 해석하면 안 됩니다.

조회된 축제: 담양 국가유산야행, 2026섬진강국제실험예술제(SIEAF), 함평모악산 꽃무릇축제.
두 외부 주소는 현재 GitHub ver4 원본에도 동일하게 들어 있습니다. **네이티브 전환 때문에 빠진 연결이 아니라 공통 서버의 현재 호출 주소/권한 문제**입니다.
키는 기존 `DATA_GO_KR_KEY`를 사용하며 출력하지 않았습니다. 동일 키로 국문 TourAPI는 성공하므로 모든 서비스의 키가 잘못됐다고 단정하지 않습니다.
공공데이터포털의 신청 상세에서 각 서비스의 최신 요청 주소·오퍼레이션·승인 상태를 대조해야 합니다. 공식 문서도 서비스 없음은 호출 URL, 등록되지 않은 키는 해당 서비스 신청/키 상태를 확인하도록 안내합니다. [관광사진 공식 안내 및 오류표](https://www.data.go.kr/data/15101914/openapi.do)

### 남은 웹/네이티브 차이

- 웹 상세에 있는 관람 소요·관람 연령·휴무·공식 안내 링크·연관 카드 일부는 네이티브 상세에 표시하지 않습니다. 응답 모델은 해당 필드를 읽지만 UI가 전부 사용하지는 않습니다.
- 네이티브 갱신 날짜는 UTC 문자열 앞부분을 잘라 표시해 한국 시간 오전에 하루 전으로 보일 수 있습니다.
- 사진 표시/출처 표기 확인은 개별 사진의 상업 이용 조건 검토 완료와 같지 않습니다.

실기 재검사: S20+ `LiveFlowTest` **1개 통과, 23.302초**. 홈 실제 배경·축제 상세 사진·실제 코스·두 번째 지도 확인. 이번에는 기능 추가 없이 기존 네이티브 화면을 검사했습니다.
원본: `.runtime/home-audit/integrations.json`, `01-home.png`, `01b-hot-place-detail.png`, `03b-course-detail.png`.
재현: `node --import tsx scripts/check-home-integrations.mjs` (읽기 전용 API 호출).

## 3. 팀원 뚜벅이 점수 적용 여부

GitHub 최신 `ver4`를 fetch만 하고 병합/덮어쓰지 않았습니다. 확인 커밋은 `983c023a626c01785b5cfc04f2a7e88c43223d1f`입니다.
현재 `recommendScore.ts`, `walkability.ts`, `rankCourses.ts`는 이 원격 버전과 차이가 없습니다.

각 세부 항목을 0~100점으로 표준화한 뒤 다음 가중합을 반올림합니다.

| 항목 | 가중치 |
| --- | ---: |
| 걷기 부담 | 35% |
| 대중교통 | 25% |
| 이동 시간 | 15% |
| 환승 | 10% |
| 거리/숙소 | 5% |
| 체류 효율 | 10% |

최종 코스 추천 점수는 별도로 **취향 40% + 뚜벅이 35% + 시간 적합도 15% + 코스 품질 10%**입니다.
과거 3항목 가중합 함수 `weightedWalkabilityScore`는 남아 있지만 현재 서버의 최종 순위 계산에서 호출하지 않습니다.
실제 경로는 `/api/recommend` → `rankCourses` → `evaluateCourse` → 6항목 `walkingScore`입니다.

네이티브는 API의 `walkingScore`, `walkingBreakdown`을 읽어 코스 카드와 상세에 표시하며 별도로 옛 계산식을 적용하지 않습니다. 상세에는 6개 표준 점수와 종합/뚜벅이 구분이 있습니다. 웹의 별점 UI와 모양은 같지 않습니다.
실제 코스 **5개 모두** 세부 점수로 다시 계산한 값이 API 값과 일치했습니다. 예: 63/87/87/100/81/100의 가중합은 80.9 → **뚜벅이 81점**, 종합은 **73점**. S20+ 상세의 81점/73점과도 일치했습니다.
데이터가 없는 배차 간격 등에는 기본 추정점수가 들어가므로 현장 실측 정확성을 보장하는 점수는 아닙니다.

원본: `.runtime/home-audit/walking-scores.json`. 재현: `node scripts/check-walking-score.mjs`.
추가 Kotlin 계약 검사: `TravelContractTest.sixComponentWalkingScoreIsPreservedFromServer`. Android 단위 검사 전체 **31개 통과**(프로젝트 캐시로 오프라인 빌드, 휴대폰 불필요).

## 휴대폰 없이 검사하는 범위

- PC 웹/개발 서버: 화면의 웹 버전, 실제 API, 조건 보정, 점수 계산, DB 계약, 모델 응답, 대부분의 자동 검사 가능.
- Android 단위 검사: 휴대폰 없이 Gradle로 실행 가능.
- 네이티브 화면·카카오 지도 SDK·소셜 로그인 복귀/권한: 실기 또는 Android 에뮬레이터 필요. 현재 APK는 S20+ 검증용 arm64 빌드여서 PC의 x86 에뮬레이터는 별도 빌드 설정 검토 필요.
- 설치된 S20+ APK는 HTTPS 개발 공유 주소를 사용하므로 USB 없이도 접속 가능. PC의 API 서버/터널이 켜져 있어야 하며 임시 주소가 바뀌면 앱 설정 재반영 필요. 개발용 접속 키가 든 APK는 공개 배포 금지.
